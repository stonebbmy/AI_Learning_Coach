本仓库网络约定（默认「兜底」）：
• **拉镜像**：compose 默认使用 **DaoCloud** 前缀的镜像名（与 Docker Hub 同源），降低国内直连 registry 的失败率；可在 .env 中改回官方名。
• **构建期**：ai-service 使用 **清华 Debian + 清华 PyPI**（pip wheel 层 **不** 注入 HTTP 代理，避免经 Clash 访问 pypi.org 的 SSLEOF）；java-app 使用 **清华 Ubuntu apt + 阿里云 Maven**。
• **运行期**：业务外网（大模型、MCP、嵌入 API 等）经 compose 注入的 **DOCKER_*** 代理访问本机 Clash（端口默认 7890，**Allow LAN**），与 NO_PROXY 中的内网/API 例外并存。

────────────────────────────────
一、Docker Desktop（Windows）
────────────────────────────────
1. Settings → Resources → Proxies
   - Manual：HTTP / HTTPS 均填  http://127.0.0.1:7890
   - 端口与 Clash「Mixed」一致。
2. Settings → Docker Engine
   - 本仓库 compose 已默认 **DaoCloud 镜像前缀** 拉取与 Docker Hub 同源的镜像；若你额外配置了 registry-mirrors，可与 compose 并存，以实际拉取成功为准。
   - build / pull 报 auth.docker.io、registry-1.docker.io 经 IPv6 超时：在 JSON 中合并 docker/docker-desktop-engine.example.json 里的字段（与现有内容合成一个 JSON，勿覆盖其它键），重点是 "ipv6": false 与可选 dns；保存后 Apply & Restart。
3. Apply & Restart。
4. Settings → Resources → Network（Configure the way Docker containers interact with the network）
   - Docker subnet 192.168.65.0/24：一般保持默认即可；除非你本机其它网段与该段冲突，再改。
   - Enable host networking：未在 compose 里使用 --network host 时不必开；保持关即可。
   - Port binding behavior：默认（局域网可访问映射端口）适合本机开发；若只希望本机访问映射端口、不让局域网其它机器访问，可改为仅 localhost。
   - Default networking mode：选 ipv4only 与「减少 IPv6 带来的 registry/解析问题」一致，建议保持。
   - Inhibit DNS resolution for IPv4/IPv6：保持 auto 即可；若容器里仍出现 AAAA/IPv6 相关异常，再按界面说明尝试更偏 IPv4 的选项。

────────────────────────────────
二、WSL2（在 Linux 发行版里开发、跑 docker / curl / pip 时）
────────────────────────────────
1. 复制 docker/wsl-proxy.env.example 为 ~/.wsl-proxy.env，按需改 CLASH_PORT。
2. 在 ~/.bashrc 或 ~/.zshrc 末尾增加：
     [ -f ~/.wsl-proxy.env ] && . ~/.wsl-proxy.env
3. 新开终端后执行：curl -I https://www.google.com  验证（需 Clash 规则允许）。
说明：
   - 默认 WIN_HOST 取 /etc/resolv.conf 里 nameserver（多为 Windows 主机在 WSL 中的地址），用于访问 Windows 上监听的 Clash。
   - 若你使用 Windows 11「镜像网络」等，有时可直接用 127.0.0.1:7890，可把 ~/.wsl-proxy.env 里改为 export http_proxy=http://127.0.0.1:7890 自行试验。

────────────────────────────────
三、本项目（docker compose）
────────────────────────────────
1. 复制根目录 .env.example 为 .env。
2. DOCKER_HTTP_PROXY / DOCKER_HTTPS_PROXY 默认指向 host.docker.internal:7890（容器访问宿主机 Clash）。
3. 若 Clash 端口不是 7890，只改 .env 中端口即可。
4. compose 已为 ai-service / java-app 配置 extra_hosts: host.docker.internal:host-gateway；**docker compose build** 的 build 段同样配置了 extra_hosts（本仓库已加），否则构建容器内无法解析 host.docker.internal，代理环境变量将失效。
5. 若 **docker pull** 仍 TLS 超时：在 Docker Engine 侧检查 **proxies**（建议 host.docker.internal）、**ipv6: false**、Clash **Allow LAN**；构建期 apt/pip/mvn 已默认走国内镜像，一般不再依赖 pypi.org 经代理。

四、全流程逐步排查（推荐）
────────────────────────────────
见 docker/FULL-STACK-CHECKLIST.txt（从 Docker Engine、宿主机 curl、pull、build、up、e2e 顺序）。

────────────────────────────────
五、快速自检
────────────────────────────────
- Windows CMD： curl -I https://registry-1.docker.io/v2/
- 项目根目录： docker compose build --no-cache ai-service  （应能拉 base 镜像并 pip）
- 容器内端到端（代理 + MCP 外网）：先 docker compose up -d redis chroma ai-service，再执行
    docker exec aicoach_ai_service sh -c "cd /app && PYTHONPATH=/app python /app/scripts/e2e_network_check.py"
  若 docker build 报 auth.docker.io 通过 IPv6 超时，可在 Docker Engine 里为 daemon 关闭 IPv6 或检查本机 IPv6 与代理是否兼容。

────────────────────────────────
六、「业务外网」指什么（和 build / 探测的区别）
────────────────────────────────
- 「业务外网」= 应用跑起来之后，为完成产品功能需要访问的公网：例如大模型 API、嵌入 API、MCP/DuckDuckGo 搜索、向量库等。这些走你 compose 里配的容器代理、或 NO_PROXY 里直连的国内 API 即可；用 e2e_network_check.py 或真实调接口验证即可。
- 「不是」必须强求：容器里 curl google.com、或任意公网站点都 100% 成功；那只是通用探测，与是否完成本项目的业务无关。
- Docker build / docker pull 访问 Docker Hub（auth.docker.io）失败，属于「引擎拉镜像」问题，与上面「业务进程外网」是两条链路；见下节。

────────────────────────────────
七、Docker build / pull 仍失败（TLS 超时、连不上 registry）
────────────────────────────────
现象：build 在拉取 FROM / 元数据阶段报错，含 auth.docker.io、registry-1.docker.io、TLS handshake timeout。

原因说明（Windows Docker Desktop）：
- 拉镜像的是 Docker 内置 Linux VM 里的 **daemon**，不是 Windows 本机进程。
- 若在 Docker Engine 里写 **http://127.0.0.1:7890**，在部分版本/路径下会指向 **VM 自己的环回口**，上面没有 Clash，代理实际未生效，外网仍异常。
- 更稳妥：daemon 的代理写成 **http://host.docker.internal:7890**（指向 **Windows 宿主机** 上的 Clash Mixed 端口），并开启 Clash **Allow LAN**。

建议的 Docker Engine JSON（与现有字段合并，勿删你已有 builder 等键；键名以你 Docker Desktop 版本为准）：
- "ipv6": false（你已配置，保留）
- "dns": ["8.8.8.8","1.1.1.1"]（你已配置；若在国内 DNS 仍异常可再试 223.5.5.5）
- "proxies": 见仓库 docker/docker-desktop-engine.example.json：**重点把 http/https-proxy 从 127.0.0.1 改为 host.docker.internal**；**no-proxy** 建议包含 127.0.0.11（容器内 DNS）、.docker.internal，避免误把 Docker 内部解析走代理。

Resources → Proxies（界面）与 Docker Engine → proxies（JSON）二选一或保持一致即可；若两处都配，以实际生效为准，避免互相矛盾。

Clash 侧：
- 确认 **docker.io、registry-1.docker.io、auth.docker.io、production.cloudflare.docker.com** 等走代理或能连通（看 Clash 日志 / 连接记录）。
- 规则若把上述域名设为 DIRECT 且直连失败，会表现为 TLS 超时。

仍失败时：
- 重试：docker compose build --no-cache ai-service
- 检查 Docker Engine **proxies**、**ipv6: false**、Clash **Allow LAN**
- 本仓库 compose 已默认 **DaoCloud** 镜像名；仍可在 Engine 中配置 **registry-mirrors** 作为环境级补充

────────────────────────────────
八、已知现象（容器内通用站点）
────────────────────────────────
- 容器内「仅环境变量、不显式指定 proxy」访问个别站点（如 google.com）可能出现 TLS 握手超时，而同环境访问 DuckDuckGo 正常；与站点/IPv6/路由有关。不影响「六」中的业务外网判定时，可忽略。
